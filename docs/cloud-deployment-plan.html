消费者运营中台 - 云端部署方案

容器化架构 / 分阶段扩容 / 可复制可回滚

核心原则：所有服务 Docker 容器化，docker-compose.yml 一键编排。换服务器只需一条命令 docker compose up -d 启动全套环境。数据与服务分离，后期按角色拆机扩容，不影响已有架构。

二、为什么用 Docker 容器化

维度容器化方案传统裸装方案
可复制性一份 docker-compose.yml + .env，任何服务器一键启动每台服务器手动装环境，容易不一致
扩容任意容器拆到新机器，改网络配置即可重新部署整套环境
稳定性容器崩溃自动重启，互不影响一个服务挂可能拖垮全机
回滚切上一个镜像版本，10 秒回滚重新装包，手动排查
迁移docker save → scp → docker load，整环境搬迁从头搭建

三、分阶段扩容路线

阶段一 单机部署（3-5 个客户，现在启动）

一台服务器跑全套容器，最经济、最简单。足以支撑 3-5 个品牌客户同时使用，包括知识库检索、策略生成、飞书下发。

腾讯云 CVM CPU：4 核 内存：16 GB 磁盘：100 GB SSD 带宽：5 Mbps 起 系统：Ubuntu 22.04 LTS GPU：不需要 容器内存分配： nginx ~200 MB fastapi (4w) ~2 GB postgresql ~4 GB （含 pgvector 向量索引） redis ~512 MB embedding ~2 GB （nomic-embed-text, CPU 推理） signal-crawler ~1 GB （Playwright 无头浏览器，定时抓取公开数据源） ───────────────────────── 合计 ~10 GB，16 GB 留足余量

不需要 GPU 的原因：LLM 生成走云端 API（DeepSeek / GLM），不占服务器算力；Embedding 用 nomic-embed-text（136MB 小模型），CPU 推理一次几十毫秒；向量检索在 PostgreSQL 内完成。

阶段二 数据库分离（10-20 个客户）

数据量增大后，把 PostgreSQL 和 Embedding 服务拆到独立机器，应用层保持无状态，可随时加机器做负载均衡。

服务器 A（应用层） 4 核 / 8G / 50G SSD nginx + fastapi + redis 无状态，可随时复制加机器 服务器 B（数据层） 4 核 / 16G / 200G SSD postgresql + pgvector（主库） embedding 服务 数据有状态，需定期备份

扩容操作：应用层加一台同配置 CVM，挂到腾讯云 CLB 负载均衡后面，零代码改动。

阶段三 横向扩展（50+ 个客户）

全链路水平扩展，每个角色都可独立扩容，支撑大规模客户量。

负载均衡 腾讯云 CLB ├── 应用服务器 A (nginx + fastapi) ├── 应用服务器 B (nginx + fastapi) └── 应用服务器 C (nginx + fastapi) 数据库主从 PostgreSQL 主库（写入） PostgreSQL 只读副本（查询，含向量检索） 缓存与队列 Redis 集群（缓存 + 异步任务） Embedding 服务 独立实例 ×2 副本（可继续加） 信号采集服务 signal-crawler 独立实例 ×2（多品牌并发抓取） 文件存储 COS + CDN 加速 可选升级 向量量超百万级时：pgvector → Milvus 专业向量数据库 客户量上百时：Docker Compose → Kubernetes 编排

六、信号中心数据与采集

需求飞轮的信号中心会持续采集市场信号，这些数据与业务数据共同存储在 PostgreSQL 中，无需独立数据库。

数据量评估

数据表当前数据量含义年增长预估（5 客户）
demand_signals211 行 / ~40 KB原始市场信号文本~50 MB
demand_profiles1,464 行 / ~400 KB结构化需求画像~200 MB
demand_graph30 行 / ~9 KB需求关联关系~10 MB
hot_videos10 行 / ~2 KB热点视频榜单~50 MB
knowledge_chunks（对比）10,003 行 / ~105 MB知识库文本+向量~500 MB
信号数据合计~450 KB—~310 MB/年

结论：信号数据量远小于知识库（105 MB vs 0.45 MB），存储层面 100G SSD 绰绰有余。真正的资源消耗在采集过程本身。

采集方式与资源消耗

采集方式适用场景资源消耗是否需要额外机器
第三方数据 API蝉妈妈、巨量引擎、小红书开放平台极低，仅 HTTP 请求 + 存储否
无头浏览器爬取公开页面抓取（Playwright）~1G 内存，CPU 间歇占用否（阶段一），阶段三拆独立容器
飞书回传运营动作、客服沟通记录零（Webhook 被动接收）否
手动录入运营补充信号零否

架构考量：signal-crawler 作为独立 Docker 容器运行，使用 Playwright 定时抓取公开数据源。独立容器的好处是：爬虫崩溃不影响主 API 服务；后期可单独拆到独立服务器；可独立扩容（如多品牌并发抓取）。阶段一单机跑，16G 内存够用；阶段三按需拆机。

八、部署步骤

  • 开通腾讯云 CVM（4核 16G / 100G SSD / Ubuntu 22.04）
  • 配置安全组：开放 80、443 端口
  • 安装 Docker + Docker Compose
  • 准备 docker-compose.yml（含 nginx / fastapi / postgresql / redis / embedding 五个容器）
  • 准备 .env 配置文件（数据库密码、LLM API Key、飞书配置等）
  • 构建后端 Docker 镜像（含全部 Python 依赖）
  • 初始化 PostgreSQL + pgvector 扩展
  • 执行数据迁移脚本（SQLite → PostgreSQL）
  • 重算向量索引（nomic-embed-text 在新环境跑一遍）
  • 部署前端静态文件到 Nginx
  • 配置 SSL 证书 + 域名解析
  • 更新飞书事件订阅 URL 为云端域名
  • 健康检查 + 冒烟测试
  • 设置定时备份（PostgreSQL 每日 dump → COS）

    • 备份策略：PostgreSQL 每日自动 dump 到 COS，保留 30 天。Docker 镜像版本化管理，随时可回滚。.env 配置文件加密存储，不进 Git。

    九、启动前需要提供

  • 腾讯云 CVM 已开通（4核 16G / 100G SSD / Ubuntu 22.04）
  • SSH 登录方式（IP + 密码或密钥）
  • 域名 + 子域名（如 ops.xxx.com）
  • SSL 证书（或由我在服务器申请免费的 Let's Encrypt）
  • 飞书开放平台权限（更新事件订阅 URL）
  • 确认 COS 是否已开通（未开通可先用服务器磁盘）
