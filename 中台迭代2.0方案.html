01

现状判断 · 离客户可用还差什么

已建成（可复用）指令中心 12 维指令 · 飞轮洞察 · 需求飞轮热点+画像+货盘 · 策略沉淀 · 执行中心 7 板块排期+托管 · 护栏违禁词 · 知识库 · 多行业模板 · 验收 KPI · 本地 LLM · 飞书 webhook（部分通）
客户不可用的原因跑在个人 Mac 上 · 用本地 Ollama · 内容发不到企微 · 多品牌数据未隔离 · 全链路中间断了 · 资产包不可查看 · 无客户登录体系

五个硬卡点（不解决 = 客户无法使用）

  • 部署：系统跑在个人 Mac + Cloudflare 临时隧道，URL 会变、会断、不安全。客户需要 7×24 稳定访问的云端地址。
  • LLM：本地 Ollama qwen2.5 在个人电脑上跑，并发低、不稳定。生产环境必须用云端 API（DeepSeek / Qwen）。
  • 渠道执行：系统生成朋友圈 / 1v1 话术 / 社群内容 / 短信，但没法真正发到企微或短信通道。等于只写不发，客户看不到效果。
  • 数据隔离：只有一个 default tenant，多个客户品牌的数据混在一起，客户看到别家数据是合规事故。
  • 全链路闭环：指令→策略→审批→执行→反馈→KPI 回写这条链路中间断了，资产包点不动、执行不能自动下发、验收回不来。

核心原则：P0 解决"能不能用"，P1 解决"好不好用"，P2/P3 解决"能不能长大"。先把 P0 做完，客户就能上手用了；P1 跟上让体验到位；P2/P3 再追策略自生长和生态。

P0 · 2-3 周 商业 MVP 硬卡点 — 客户能真正跑起来

目标：系统部署到云端，客户登录后能看到自己的品牌数据，下发指令后能生成策略，审批后能自动执行到企微，执行结果回流到验收。

P0-1 云端部署系统部署到腾讯云（公司云），绑定子域名 + HTTPS。launchd 换成 systemd / Docker。SQLite 迁移到云数据库（PostgreSQL 或云 MySQL）。前端 dist 由 Nginx 托管。
P0-2 LLM 切云端 API本地 Ollama 替换为 DeepSeek API（或 Qwen API）。LLM Gateway 加 cloud 模式，按品牌计量 token。保留本地模式做开发调试。
P0-3 企微真实执行接入企业微信 API：朋友圈发布、1v1 消息推送、社群消息推送。执行中心的"立即下发"按钮对接真实渠道。执行结果写入 feedback_events。
P0-4 多租户数据隔离每个客户品牌 = 独立 tenant_id，所有 API 按当前 tenant 过滤。品牌切换时数据不串。数据库层面加 tenant_id 外键约束。
P0-5 全链路闭环修通资产包查看 → 审批 → 执行中心分类展示 → 自动下发 → 飞书/企微回传 → KPI 回写 → 策略效果记录。中间断的环节全部接上。
P0-6 客户登录体系品牌级账号：admin（代运营）/ operator（品牌运营）/ viewer（品牌查看）。品牌用户只看自己品牌的数据。JWT 签发带 tenant_id。

P1 · 3-4 周 生产可用 — 客户用着舒服

目标：客户用起来不卡、不乱、不担心成本。内容质量从"能看"到"能用"。飞书回流做完整。

P1-1 飞书回流闭环修复 webhook 文本提取；群聊运营汇报自动解析 → KPI 回写 → 策略效果更新。支持图片/表格消息（OCR）。多群 → 多品牌映射。
P1-2 内容质量提升指令产出从模板填充升级为：读品牌知识库 + 客户画像 + 历史效果数据 → 生成行业适配的具体内容。活动策划有类型有节奏、货盘有卡项逻辑、话术有异议处理。
P1-3 成本计量每个品牌的 LLM token 消耗按调用记录，月度汇总。预算上限告警。运营人员能看到自己品牌的成本。
P1-4 客户体验打磨品牌切换全局联动、排期日历可编辑、资产包可点开查看详情、执行中心板块模板布局优化、移动端适配。

P2 · 4-6 周 规模化 — 多品牌并行 + 策略生长

目标：平台级策略资产共享，品牌分支快速派生，策略靠效果自动生长，跨行业打法复用。

P2-1 自生长策略引擎策略卡增加效果权重（runs/wins/score）。验收 KPI 回流更新权重。飞轮建议按效果排序。AI 组合已验证打法生成候选策略，人工审核后沉淀。
P2-2 平台级资产分层策略/模板/知识/护栏升级为"平台默认 + 品牌覆盖"。平台升级一次，全部品牌同步获得新能力。品牌私有覆盖不污染平台。
P2-3 品牌快速派生新客户几分钟内派生品牌分支：选行业 → 导入品牌资料 → 自动配置模板 → 生成工作台。解约只停分支，平台不动。
P2-4 跨行业复用策略节点标注行业/场景/人群/渠道，按相似度推荐复用。美业验证的打法一键适配到餐饮/零售。
P2-5 开发者后台品牌管理（派生/启停/解约/版本）、资产管理、计量对账、操作审计。仅内部使用。
P2-6 多品牌驾驶舱平台级总览：所有品牌的执行进度、KPI 达成、成本、告警。一屏看全局。

P3 · 4-6 周 生态扩展 — 渠道 + 数据 + 计费

目标：接入更多渠道和数据源，按客户计量计费，开放生态。

P3-1 短信通道容联云短信真实发送。执行中心短信板块对接。发送回执回流。
P3-2 商业数据接入巨量引擎、小红书、抖音、蝉妈妈数据按客户签约接入。数据进入飞轮信号池。
P3-3 开放 API第三方客服平台可推送信号、创建指令、查询执行结果。外部系统可调用策略生成。
P3-4 计费对账按客户出月度账单：LLM token + 短信条数 + 渠道调用。成本分摊透明。

04

与原方案对比 · 改了什么

维度原方案2.0 方案
P1 首要任务策略效果回流（内部优化）云端部署 + 企微执行（客户可用）
飞书位置P1-4 并列降为 P1-1（P0 完成后再补）
策略自生长P1 核心移到 P2（客户先用起来再生长）
企微执行P3 才接提到 P0（不发内容 = 不可用）
客户登录未明确排期P0-6 必做
商业数据P3保持 P3（非首批客户刚需）

一句话总结：原方案从"系统内部能力"出发排优先级，2.0 方案从"客户能不能用"出发排。先把硬卡点解掉，让客户上手，再追策略自生长和生态扩展。

05

P0 所需资源与依赖

公司技术配合
  • 腾讯云子域名 + SSL 证书
  • 云数据库实例（PostgreSQL / MySQL）
  • 服务器或容器服务（CVM / CloudBase）
  • 防火墙 / 安全组配置
需要申请的权限
  • 企业微信 API（通讯录/消息/朋友圈/会话存档）
  • DeepSeek API key（或 Qwen / OpenAI）
  • 飞书自建应用：群消息读取 + 发送权限
研发分工建议
  • Codex：后端全链路闭环 + 企微对接 + 数据隔离 + 前端适配
  • 公司技术人员：云部署 + 域名 + 数据库 + 安全配置
  • 运营：准备首批客户品牌资料 + 验收测试
风险与对策
  • 企微 API 有审核周期 → 尽早申请
  • 云端 LLM 成本随量涨 → P0 就建计量
  • 数据迁移风险 → 先双跑（本地+云端）验证再切
